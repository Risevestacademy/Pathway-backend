# Content Revisions

The generic revision system. One workflow, many content types.

## Concepts

- **RevisionSession** — the draft workspace. One per editor per context at a time.
  Has `contextType` + `contextId` (the career it was opened from, or a
  pre-allocated ID for new careers), used for display, querying, and publish
  ordering. Its `status` is the workflow state:
  `DRAFT → IN_REVIEW → APPROVED → PUBLISHED`, with `CHANGES_REQUESTED` and
  `REJECTED` as branches. Review decisions attach to the session.

- **ContentRevision** — one row per changed model in a session. Fields:
  `sessionId`, `contentType`, `contentId`, `baseVersion`, `snapshot` (JSON).
  Uniqueness: `(sessionId, contentType, contentId)` — at most one pending
  change per model per session. **Storage is granular; submission is batch.**

- **ContentRevisionPublishEvent** — append-only log, one row per
  (content root, publish). The current version of any `(contentType, contentId)`
  is `COUNT(*)` over this table. PUBLISHED revisions are never deleted; this
  keeps the count monotonic.

- **RevisionStrategy** — one per content type. Interface:
  `validate`, `plan`, `diff`, `apply`, `loadLive`, `lock`, `isStale`,
  `titleFor`, `tempIdFields`, `sectionLabel`, `fieldLabels`,
  `nestedRootsTouched`. Defined in `strategy.types.ts`.

  - **Source** is a content root. Editors create and edit source rows (`name`,
    `url`, `lastCheckedAt`) that outlook entries reference. A `SOURCE` revision
    is its own root; an `OUTLOOK` revision that changes `sourceId` references a
    `Source` row by real ID (no cross-revision temp IDs for sources — sources are
    created via their own session, then referenced). See
    `§Aggregate boundaries`.

## Submission — one call, one payload, one transaction

Drafts save in ONE batch call with **replace semantics**:

    POST /admin/sessions/:sessionId/draft
    { changes: [ { contentType, contentId, snapshot }, ... ] }

- The payload is the complete set of drafts for the session.
- Any existing `ContentRevision` for this session NOT in the payload is deleted
  in the same transaction. There is no separate delete-revision endpoint.
- Never touches the live tables. It only writes `ContentRevision` rows.
- Autosave is the same endpoint, debounced. Idempotent because it is a replace.
- Per-change validation warnings are returned but do not fail the save.
  Validation hard-fails on submit, not on save.

## Workflow

- **submit** — validate + plan + staleness check for every revision;
  all revisions and the session transition together. All-or-nothing.
- **review** — one `Review` row on the session; the decision transitions the
  session. Self-review is blocked. Approving publishes nothing.
- **publish** — apply all revisions in dependency order, in one transaction.
  On any failure the whole transaction rolls back; the session stays APPROVED.
- **changes requested** — the session returns to the editor, who opens a NEW
  session with the corrections. The original session and its review stay in
  history. (The original session is not re-submittable.)

## Publish order

The publisher sorts revisions by their content type's position in one of two
arrays, depending on whether the session's context row already exists:

- If the context row exists in the DB → `PUBLISH_ORDER_UPDATE`.
- If not (creating new) → `PUBLISH_ORDER_CREATE`.

  PUBLISH_ORDER_CREATE = [
  CAREER, PATHWAY, PATHWAY_STAGE, RESOURCE, SKILL,
  PATHWAY_STEP, PATHWAY_STEP_TASK, OUTLOOK,
  ]
  PUBLISH_ORDER_UPDATE = [
  RESOURCE, SKILL, PATHWAY_STEP_TASK, PATHWAY_STEP,
  PATHWAY_STAGE, PATHWAY, CAREER, OUTLOOK,
  ]

Both orders are topological sorts of the schema's FK DAG. Adding a content type
means adding it to both arrays in the correct position and writing a strategy.
Unknown content type at publish → `UNKNOWN_CONTENT_TYPE_IN_PUBLISH`.
Cycles are a schema problem, not a code problem; the publisher assumes the DAG
is valid.

## Temp IDs

- Format: `new-<n>`. Scoped to the session. Generated by the frontend.
- Each strategy declares `tempIdFields: { path, kind: 'scalar' | 'array' }[]` —
  the JSON paths in its snapshot where a `new-*` ID may appear.
- Each strategy's `apply` returns `{ createdIds: Map<tempId, realId> }`.
- The publisher maintains a session-level `tempIdMap` and rewrites each
  revision's snapshot before applying, driven by `tempIdFields`.
- The publish response includes `idMap: { [tempId]: realId }` so the frontend
  can reconcile local state.

## Versioning

- `currentVersion(contentType, contentId) = COUNT(*)` over
  `ContentRevisionPublishEvent` for that root.
- `isRevisionStale(baseVersion, currentVersion) = baseVersion < currentVersion`.
- PUBLISHED revisions are never deleted. This keeps counts monotonic.
- `Career.version` is a display mirror, set on publish for compatibility.
  Staleness uses the publish-event count for **all** content types, including
  careers.

## Shared resources

A `RESOURCE` revision updates the single `Resource` row; every career that
references it sees the change on publish. The diff includes a `SHARED_RESOURCE`
advisory ("used by N careers"). Publish does not block on this; it is an
advisory, not a blocker.

## Aggregate boundaries

- A `CAREER` revision owns only career-level fields (title, slug, description,
  targetLevels, etc.). It does **not** contain pathway, steps, resources,
  outlook. Those are their own roots, edited in their own revisions.
- A `PATHWAY` revision owns the pathway row and structural changes: which step
  is in which stage, and step ordering (`order` lives on the pathway revision,
  not on the step revision).
- A `PATHWAY_STEP` revision owns the step's own fields and its skill/resource
  links.
- `RESOURCE`, `SKILL`, `OUTLOOK`, `STAGE_QUIZ`, `QUIZ_QUESTION`,
  `PATHWAY_STEP_TASK` are each their own root.
  - `SOURCE` is its own root. Outlook entries reference sources by real ID. A
    session that both creates a source and assigns it to an outlook row uses two
    revisions; the source must publish before the outlook (enforced by
    `PUBLISH_ORDER_*`). Temp IDs for sources are not supported in v1 — the
    frontend must publish the source first, then set `sourceId` in a subsequent
    session. (If this becomes an ergonomic problem, add `sourceId` to the outlook
    strategy's `tempIdFields` and to the publisher's rewrite — one line each, in
    a later ticket.)

Cross-aggregate conflicts are prevented by the staleness check: publishing a
revision writes a publish event, which bumps the version of its root, which
makes any open revision against that root stale on submit and publish.

## Locking order

- Per-revision transitions: `strategy.lock(live row)` first, then the revision.
- Session-level operations: lock the session first, then (during publish) lock
  each live row in publish order.
- **Never** lock a live row then a session. **Never** lock two live rows in
  inconsistent order.

## Invariants

- PUBLISHED revisions are never deleted.
- Save-draft never touches the live tables.
- Publish is one transaction. Partial publishes do not exist.
- A session is the source of truth for its revisions' status.
- `currentVersion` is monotonic per root.
- Total learner XP never decreases on unmarking (see the pathway module; the
  revision system does not touch XP).
- Sources publish before outlook entries that reference them. See
  `PUBLISH_ORDER_*` and `ADR-9`.
